# חבילה 6א: יסודות שמירה בשרת

תאריך: 19.10.2026. תכולה: מימוש SQL אמיתי ובדיקתו ב־PostgreSQL מקומי מבודד. **אין אישור להריץ את הסקריפט ב־Production ואין החלפת כותב קיים בחבילה זו.**

## מה מומש

קובץ השרת הוא `supabase/staged/persistence-foundation-v1.sql`. הוא לא נמצא במסלול מיגרציות אוטומטי, אינו מיובא מקוד האפליקציה ואינו רץ ב־build. ה־schema הפרטי `persistence_v1` אינו RPC ציבורי של האפליקציה. נדרש חיבור מפורש ומאובטח בחבילה 6ב.

- `tasks.revision` ו־`subtask_number_high_water` הם bigint. גרסה ו־epoch חוזרים כמחרוזות ב־JSON, לרבות ערכים מעל דיוק Number בדפדפן.
- בקרת חשבון: enabled כבוי ו־read_only פעיל כברירת מחדל; write_epoch ו־change_seq עולים. הסקריפט אינו מפעיל חשבון כלשהו.
- counters נפרדים לבעלים ולקידומת P/W; ההקצאה מתבצעת בשרת. מחיקה אינה מורידה אותם; הרצה חוזרת של האתחול משתמשת ב־GREATEST ואינה דורסת floors שכבר הוגדלו.
- פקודות בעלים: יצירת משימה, patch מצומצם, סטטוס, מיקוד והוספה/עריכה/הסרה/סטטוס של צעד יחיד. אין החלפת רשימה או מערך צעדים מהלקוח; זהות ומספר קיימים אינם שדות patch.
- השרת בודק auth, פרוטוקול, שדות מותרים, סוגי ערכים, תאריכים, סיווג והרשאת בעלים; אין קבלת owner_id מהלקוח. פקודות שיתוף, AI, הגדרות, ייבוא ושחזור עדיין אינן נתמכות ונידחות.
- סדר נעילות: מזהה פעולה לפי actor, אחריו חשבון, אחריו יעד. פעולה אחת אינה נועלת חשבונות אחרים. הכנה לשיתוף תדרוש מיפוי בעל היעד ולא נעילת חשבון הנמען.
- receipt עם SHA-256 של JSONB קושר operationId לתוכן; הוא אינו משכפל הערות או כותרות. כתיבת המשימה, המספרים והקבלה נעשית באותה טרנזקציה. אין claim שמתחייב בנפרד. כשל כתיבת receipt מחזיר גם שינוי ומספור לאחור.
- ניסיון חוזר מחזיר את ההכרעה שנרשמה ואינו מבצע שוב. payload אחר באותו מזהה נדחה. conflict נשאר conflict גם אחרי שינוי נוסף. דחיית סיווג ידועה אינה הופכת להצלחה מאוחרת בלי מזהה פעולה ואישור חדשים.
- לפני החזרת תוכן נשמרת בדיקת בעלות נוכחית. הקבלה מחזירה revision/epoch של ההכרעה ההיסטורית, אך snapshot המשימה הוא עדכני ומורשה; הלקוח העתידי חייב להבחין ביניהם ולא להחזיר מצב ישן למסך.
- טבלאות הבקרה מוגנות ב־RLS ללא גישה ישירה ללקוח; פונקציות עזר אינן ניתנות להרצה ב־PUBLIC/anon/authenticated. רק קריאת משימה ופקודת בעלים מקבלות EXECUTE ל־authenticated ב־schema הפרטי.

## תוצאות בדיקה וגבולות הראיה

מתאם `scripts/persistence/foundation-adapter.mjs` טוען **את קובץ ה־SQL עצמו**, ללא תחליף עסקי ב־JavaScript וללא חיבור רשת. הוא משתמש ב־PGlite `0.5.8`, בנתונים סינתטיים ובזהויות auth מבודדות. הפעלת החשבון בידי המתאם נעשית רק במסד הבדיקה לאחר אימות ברירות המחדל הסגורות.

בדיקות היעד המחוברות הן T01–T07, T11, T16, T23 ו־T24: 11 מתוך 40. 29 האחרות נשארות TODO במפורש; אין ממשק מרונדר או מתאם שיתוף/AI/שחזור בחבילה 6א. F01–F11 מוסיפות בדיקות שערי הפעלה ותחזוקה, סוגי ערכים ושדות לא מורשים, הרשאות, no-op, high-water, כשל הקצאה, הרצה חוזרת, epoch, bigint ודחייה עסקית שנשארת סופית.

הרצה:

```powershell
$env:PGLITE_MODULE_PATH = '<absolute path to @electric-sql/pglite/dist/index.js>'
npm run test:persistence:foundation
```

הרצה מלאה של שכבות הרגרסיה הישנות:

```powershell
npm run test:persistence
```

בהרצה הרגילה ללא PERSISTENCE_TEST_ADAPTER מלאי היעד נשאר TODO; פקודת foundation היא שמחברת את 11 המקרים לשרת החדש. אין לייחס את ספירת TODO של פקודות שונות לאותו כיסוי. שער השחרור המלא ממשיך לדרוש את כל 40 הבדיקות וממשק אמיתי; מתאם 6א מוגדר במפורש חלקי ו־renderedUi=false.

המתאם מסדר קריאות חופפות על חיבור יחיד. זו ראיה ללוגיקת הגרסאות, האטומיות ותזמוני replay מבוקרים, **לא** הוכחת נעילות בין sessions. בדיקות התקלות מפילות טרנזקציה אמיתית או מאבדות תשובה לאחר COMMIT אמיתי. תרחיש deadlock מזריק SQLSTATE אמיתי בנקודת כתיבת הקבלה; הוא אינו יוצר מעגל המתנה אמיתי בין חיבורים. בדיקת PostgreSQL רב־חיבורית נשארת חובה לפני מעבר חי.

תוצאות בפועל: `test:persistence:foundation` החזיר 23 pass (11 בדיקות יעד, 11 F ובדיקת מלאי), אפס fail, ‏29 TODO ו־SKIP אחד לשער השחרור המלא שאינו מופעל בפקודה החלקית. `test:persistence` ללא מתאם יעד החזיר 33 pass, אפס fail ו־40 TODO. בדיקה ממוקדת של שער השחרור עם מתאם 6א ו־PERSISTENCE_REQUIRE_TARGET=1 נכשלה בקוד 1 כמצופה: כיסוי חלקי וללא UI אינו מוכנות לפריסה חיה.

אימות בענף הפרסום הנקי: `npm run lint` ו־`npm run build -- --webpack` עברו, כולל TypeScript ויצירת כל הדפים. Webpack נבחר לבנייה המקומית בגלל מגבלת Turbopack הידועה על קישור node_modules של ה־worktree; תצורת הפרויקט לא השתנתה. manifest השינויים אינו כולל קוד src, נתוני אמת או טיוטות מדיניות. אין זרימת UI חדשה ל־QA דפדפן; ה־QA של 6א הוא הרצת פקודות השרת במסד המבודד, ולא בדיקת מסך שמתחבר אליו.

## גבולות שלא השתנו

1. אין בקשה או מיגרציה למסד Supabase חי; אין נתוני אמת, סודות, AI, Drive או חיוב בבדיקות.
2. REST/RPC הישנים ממשיכים להתקיים במוצר הקיים. הם עדיין עוקפים revisions/counters משום שלא הוחלף נתיב כתיבה. אין להפעיל את הבסיס החדש לצד כותבים ישנים בלי שער המעבר בחבילות הבאות.
3. אתחול המונים ממספרים ששרדו במסד אינו מוכיח מה היה המספר הגבוה שנמחק בעבר. לפני הפעלה נדרשת קביעת floors מפורשת מול תיעוד/יצוא והעלאתם לפי הצורך, לעולם לא הורדה. אין הקצאה חיה בחבילה זו.
4. הסקריפט מוסיף עמודות; כלי הגיבוי הנוכחי מזהה drift בצדק. יש לעדכן export ושחזור ב־6ב ולתרגל לפני שימוש, לא להסתמך על גיבוי ישן ככיסוי לעמודות/ledger/counters החדשים.
5. אין מחיקת ledger אוטומטית או TTL; שימור dedup ומדיניות מחיקת חשבון יטופלו יחד. receipts אינם היסטוריית עריכה מלאה.
6. פקודת SQL מחזירה תוצאה מתוך טרנזקציה; רק transport שהמתין ל־COMMIT רשאי לפרסם הצלחה. המתאם בודק זאת; חיבור HTTP/RPC ב־6ב חייב לשמר זאת ולא להזרים הצלחה מוקדם.
7. יש להקים בקרת חשבון ומונים גם לחשבונות חדשים לפני הפעלה. אין כאן trigger אוטומטי על auth.users או אפשרות לקוח להפעיל את עצמו.

## מגבלות קלט במימוש המדורג

מעטפה עד 64 KiB בייצוג JSONB טקסטואלי, title/category/actionType עד 1,000 תווים, notes עד 32,000 תווים; תאריכים הם YYYY-MM-DD או null. אלו מגבלות שרת קונקרטיות שנבדקות כאן, לא SLA ולא שינוי UI פעיל. שכבת HTTP ב־6ב חייבת להגביל גם את גוף הבקשה לפני parse ולהציג שגיאה תואמת. מספרי משימות וצעדים מוגבלים כרגע ל־2,147,483,647 בהתאם ל־integer הקיים וללקוחות; מיצוי נכשל ומחזיר את הטרנזקציה לאחור, בלי מחזור. גרסאות/epochs נשארים bigint; overflow אינו נבלע להצלחה.
