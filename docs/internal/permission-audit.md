# Permission Audit - 2026-08-28

מטרת המסמך: לתעד את מצב ההרשאות בין משתמשים לפני הרחבת יכולות שיתוף.

## ממצאים בקוד

- קריאת וכתיבת משימות מתבצעת דרך Supabase client רגיל, ללא service role בצד לקוח.
- `/api/assistant` דורש Bearer token ומאמת אותו מול Supabase לפני פנייה לספק AI.
- נתוני המשימות שנשלחים ל-AI מגיעים מהלקוח המחובר, וה-API אינו מקבל user id חופשי מהדפדפן.
- `tasks`, `user_settings`, `user_devices`, `task_taxonomy_items`, `assistant_threads`, `assistant_messages` ו-`assistant_actions` מוגנים ב-RLS לפי `auth.uid()`.
- `task_shares` מאפשר קריאה לבעלים, לנמען לפי user id, או לנמען לפי מייל מאומת.
- משתתף בשיתוף לא מקבל `update` רגיל על `tasks`; עדכון צעד טיפול משותף עובר דרך RPC מוגבל.

## ממצאים במנגנון AI

- ה-AI לא מקבל פעולה למחיקת משימה.
- פעולות גורפות כמו מחיקה/ביטול/סגירה של כל המשימות נחסמות גם בהנחיות וגם בסינון server-side.
- כל פעולה שמגיעה מה-AI נשמרת כהצעה ומבוצעת רק אחרי אישור משתמש.
- פעולות רגישות בצד הלקוח דורשות אישור נוסף בדיאלוג דפדפן.

## מה עדיין דורש אימות ידני

- להתחבר עם משתמש א' ולוודא שרואים רק את המשימות שלו.
- להתחבר עם משתמש ב' ולוודא שרואים רק את המשימות שלו.
- לנסות לשנות ידנית מזהה משימה/שיתוף דרך DevTools או בקשת REST ולוודא ש-Supabase מחזיר שגיאת הרשאה.
- אחרי השלמת UI השיתוף, לבדוק שמשתתף יכול לעדכן רק סטטוס של צעד טיפול דרך RPC, ולא לערוך/למחוק את המשימה הראשית.
