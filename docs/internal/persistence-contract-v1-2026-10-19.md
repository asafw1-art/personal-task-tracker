# חבילה 3: חוזה שמירה v1

תאריך: 19.10.2026. סטטוס: תכנון הנדסי הושלם; **לא מומש ולא נפרס**. כל שמות הפקודות, השדות והתוצאות החדשים במסמך הם ממשק יעד, לא יכולות קיימות. אין כאן SQL להרצה או אישור למיגרציה.

מקורות: `storage-write-map-2026-10-18.md`, `security-snapshot-closure-2026-10-19.md`, `recovery-readiness-2026-10-19.md`, `known-decisions.md`, מודל Task ומסלולי השמירה הנוכחיים. Next/Supabase/Vercel נשמרים; אין שכתוב או שירות חיצוני חדש.

## 1. החלטות בסיס ותנאי בטיחות

| כלל | חוזה מחייב למימוש |
|---|---|
| מקור סמכות | PostgreSQL מאשר שינויים. localStorage הוא מטמון/טיוטה, לא מקור לעדכון רשימה שלמה |
| הצלחה | רק תוצאת שרת לאחר COMMIT מוצגת כ״נשמר״. הופעה במסך, שמירה בדפדפן ותשובת מודל אינן התחייבות לענן |
| יחידת שינוי | פקודה מפורשת עם target ו־patch/פעולה מוגדרים; אין upsert של רשימת משימות ואין החלפת מערך צעדים שהגיע מהלקוח |
| התנגשות | אין last-write-wins ואין דריסה אוטומטית. נשמרת הטיוטה ומוצגים בסיס העריכה, המצב העדכני והכוונה המקומית לפני הכרעה |
| מזהים | UUID המשימה, בעליה ו־P/W קיימים אינם משתנים. P019/P-019/P-0019 מנורמלים ל־P19, וכך W |
| מספור | שרת מקצה מספרים לפי משתמש וקידומת, וכן צעדים לפי משימה. מספר שהתחייב אינו ממוחזר לאחר סיום/ביטול/מחיקה |
| ללא חיבור | מותר לשמור טיוטה. אין יצירת מספר P/W סופי ואין הבטחת שמירה בענן. אין הרחבה לעריכת offline מלאה |
| ניסיון חוזר | אותה פעולה שנשלחה חוזרת עם אותו מזהה ואותו תוכן; אין הפעלה כפולה גם אם התשובה אבדה |
| הרשאות | נבדקות מחדש בתוך הטרנזקציה. UUID, גרסה ומזהה פעולה אינם הוכחת הרשאה |
| מעבר | מותר חלון קריאה בלבד מתואם, אחרי גיבוי ותרגול. אין עצירה או כתיבה ב־Production בחבילה זו |

היקף השימוש שתועד: כ־5 רשומים, כנראה אסף בלבד פעיל, בנייד ובמחשב. לכן מותר להתחיל בתיאום כתיבות ברמת חשבון בעל המשימה, לא בנעילה גלובלית לכל המשתמשים. אין צורך כעת ב־CRDT, תור חיצוני או מסד חדש.

## 2. מודל הסמכות והגרסאות

- `task.revision`: מספר שלם עולה בשרת, החל מ־1. שינוי תוכן, סטטוס, מיקוד הבעלים או צעדים מעלה אותו פעם אחת בטרנזקציה. no-op שאושר מול הגרסה הנכונה מקבל receipt אך אינו חייב להעלות גרסה.
- גרסאות הן bigint במסד ומחרוזות עשרוניות ב־JSON, כדי לא להסתמך על דיוק Number בדפדפן. `updated_at` נשאר מידע תצוגה, לא מנגנון השוואה.
- זהות צעד קיימת נשמרת בדיוק. הצעדים יכולים להישאר JSONB בשלב זה, אבל רק השרת מעדכן צעד מסוים לפי id יציב. אין חובה להעבירם לטבלה כדי לתקן את חוזה השמירה.
- `subtask_number_high_water`: חסם עליון עולה לכל משימה, גם לאחר הסרת צעד. מספר התצוגה וה־id אינם משתנים כשמסדרים צעדים. אין שימוש ב־max של המערך שנותר כמקצה.
- מונה P/W עולה לכל בעלים וקידומת; מונה אינו נגזר מהתצוגה המסוננת ואינו נסוג בשחזור. פערים במספור מותרים; רצף ללא חורים אינו דרישת מוצר.
- מצב כתיבה לחשבון כולל `write_epoch`, מצב normal/read_only ו־`change_seq` עולה. הוא אינו משוחזר לערך ישן מתוך קובץ גיבוי. שם ומיקום הטבלה ייקבעו במימוש, לא נוצרת כאן טבלה.
- שינויים בהרשאה/הקצאה המשפיעים על ביצוע במשימה נועלים את אותו גבול חשבון ומעלים את גרסת המשימה, כדי שתצוגה ואישור ישנים לא יתעלמו משינוי ההקצאה. מיקוד אישי של נמען נשאר נפרד ממיקוד הבעלים ומגרסת תוכן המשימה.
- taxonomy והגדרות מקבלים גרסאות עצמאיות. שינוי הגדרה אינו דורש כתיבת משימות. rename רחב בודק גם את גרסת taxonomy ואת גרסאות המשימות המושפעות.

גבול החשבון לכל פקודה נקבע בשרת לפי בעל המשימה, לא לפי user_id שהלקוח שלח. משתתף בשיתוף מחויב לאותו מצב כתיבה/epoch של בעל המשימה. קבלות התראות, heartbeat מכשירים וניטור אינם הופכים לעדכוני task revision; הם נשארים מסלולים נפרדים.

## 3. מעטפת פקודה ותוצאה

דוגמה סינתטית לממשק לוגי בלבד; נתיב HTTP או RPC מדויק ייקבע בחבילה 6:

```json
{
  "protocolVersion": 1,
  "operationId": "11111111-1111-4111-8111-111111111111",
  "kind": "patch_task",
  "targetTaskUuid": "22222222-2222-4222-8222-222222222222",
  "expectedRevision": "17",
  "expectedWriteEpoch": "3",
  "patch": { "title": "משימת בדיקה" }
}
```

אין owner ID, completed_at או מספר משימה הניתנים לשינוי ב־patch. שדות לא מוכרים נדחים; שדה חסר נשאר ללא שינוי ו־null מפורש מנקה רק שדה שמותר לנקות. אין fallback שמשמיט שדה שאינו מותקן כדי להציג הצלחה.

| תוצאה | משמעות והתחייבות |
|---|---|
| `committed` | COMMIT הצליח; חוזרים operationId, זהות יעד, revision, writeEpoch ותוצאה סמכותית שמותר למשתמש לראות |
| `conflict` / 409 | הגרסה שונה; לא הוחל שינוי. מוחזר מידע להשוואה רק אם עדיין מותר לקרוא את המשימה |
| `stale_epoch` / 409 | המכשיר קודם לשחזור/מעבר. אין החלת פקודות חדשות ממנו עד רענון ובחינה מחדש של הטיוטה |
| `not_found_or_forbidden` / 404 | אין גישה ליעד או שאינו קיים; אין לחשוף דרך ההודעה או ה־diff נתון שאינו מורשה |
| `validation_failed` / 422 | השדות/הפעולה אינם תקינים; אין שינוי חלקי |
| `idempotency_mismatch` / 409 | operationId כבר נקשר לתוכן אחר; אין שימוש חוזר בו לשינוי חדש |
| `account_read_only` / 423 | כתיבה נעצרה לתחזוקה; הטיוטה נשמרת, אין הודעת הצלחה |
| `client_upgrade_required` / 426 | פרוטוקול לא נתמך; נדרש רענון. header לבדו אינו מנגנון הגנה |
| timeout / ניתוק / 5xx | תוצאה לא ידועה ללקוח. אין להסיק שהפעולה בוטלה או ליצור פעולה חדשה |

הלקוח מחיל תשובות רק על החשבון/epoch המתאימים ולא מחליף revision חדש בישן. תשובה חוזרת מה־ledger יכולה לתאר הצלחה ישנה; אם כבר נראתה גרסה מתקדמת יותר, שומרים אותה ומרעננים במקום להחזיר את המסך אחורה.

## 4. טרנזקציה ומניעת ביצוע כפול

1. אימות המשתמש והפרוטוקול, פענוח סוג פקודה מצומצם ואימות מבנה; לא בוטחים ב־snapshot או בתפקיד מהדפדפן.
2. קישור אטומי של `(actor_user_id, operation_id)` ל־hash של התוכן המנורמל, הכולל kind, יעד, epoch וגרסאות. שתי בקשות זהות ממתינות לאותה הכרעה ולא מבצעות פעמיים.
3. בדיקת הרשאה ראשונית, כניסה לתיאום הכתיבה של חשבון היעד ובדיקה חוזרת של זהות/בעלות/שיתוף/הקצאה/מצב read_only/epoch בתוך הטרנזקציה.
4. בדיקת הגרסה הצפויה, הקצאת מספרים אם צריך, החלת השינוי הממוקד וכללי הסטטוס, ועדכון הגרסאות והמונים הרלוונטיים.
5. שמירת receipt של התוצאה ו־change_seq באותה טרנזקציה; החזרת הצלחה רק אחרי COMMIT. אין מצב שבו receipt אומר done ושינוי המשימה לא התחייב.

סדר הנעילות חייב להיות אחיד בכל הכותבים: קישור הפעולה, בקרת חשבון/חשבונות בסדר קבוע, ואז יעדים בסדר UUID קבוע. אין להחזיק טרנזקציה בזמן קריאה למודל, Google או פעולה חיצונית. deadlock/serialization failure מבטלים את כל הטרנזקציה; ניסיון חוזר משתמש באותו operationId.

מצב ביניים של פעולה אינו מתחייב בנפרד מהשינוי העסקי. קישור מבוטל יחד עם rollback לא צפוי. שגיאה עסקית סופית אחרי קבלת פקודה תקינה יכולה להישמר כ־receipt דחייה באותה טרנזקציה ללא שינוי המשימה; אותה פעולה לא תהפוך להצלחה מאוחרת בלי אישור וכוונה חדשים. שגיאת auth או מעטפת לא תקינה אינה יוצרת receipt תחת זהות לא מאומתת.

לאחר אובדן תשובה, הלקוח מבקש מצב לפי operationId ויכול לשלוח שוב בדיוק את אותה פקודה. היעדר receipt ברגע הבדיקה אינו מוכיח שהבקשה הראשונה לא רצה. השרת רשאי עדיין להיות באמצע טרנזקציה; unique/נעילות חייבים להכריע זאת.

receipt כולל מינימום: actor, מזהה פעולה, hash, סוג, יעד, תוצאת התחייבות/דחייה וגרסאות. לא לשכפל בו הערות או שיחות ללא צורך. אין TTL אוטומטי למזהי dedup לפני שקיים חוזה בטוח לדחיית פעולות ישנות; מחיקת ה־ledger לא יכולה לאפשר ביצוע מחדש. מדיניות מחיקת חשבון והגנת פרטיות חלות גם עליו.

בחזרת receipt נבדקת שוב הרשאת הקריאה. אם הגישה לשיתוף בוטלה, לא מוחזר snapshot ישן שמכיל תוכן; לכל היותר אישור תפעולי מצומצם על פעולת המשתמש, או תשובת חוסר גישה. אין לבצע שוב את הפעולה בשל חוסר גישה לתוצאה.

## 5. סוגי פקודות וכללי התחום

| פקודה לוגית | סמכות ושדות | אטומיות וכללים |
|---|---|---|
| create_task | בעל חשבון; שדות תוכן מאומתים, ללא מספר סופי מהלקוח | UUID ומספר מהשרת, revision=1 ו־receipt יחד. טיוטה מקבלת מזהה זמני שאינו P/W |
| patch_task | בעלים; title/category/actionType/priority/notes/dueDate בלבד | צפוי revision; משנה רק שדות שנשלחו; category/actionType בודקים taxonomy עדכני |
| set_task_status | בעלים; enum מפורש | statusChangedAt ו־completedAt נקבעים בשרת; סיום/ביטול משמרים היסטוריה |
| set_owner_focus | בעלים; boolean | פקודה אחת, לא save מפורש ועוד effect; אינה מחליפה מיקוד של נמען |
| add/patch/remove_subtask | בעלים; צעד אחד לפי id | מספר חדש מהשרת, id קיים נשמר; הסרה מסיימת הקצאות ושומרת high-water; אין החלפת כל מערך הלקוח |
| set_subtask_status | בעלים או contributor מורשה לפי כללי ההקצאה הקיימים | פקודה מפורשת ולא toggle; בדיקה מחדש בתוך הנעילה; עדכון צעד והשלכתו על המשימה יחד |
| assign/unassign_subtask | בעלים | הקצאה תקפה לנמען accepted; שינוי והיסטוריה, גרסת משימה ו־receipt יחד |
| invite/accept/decline/revoke/leave_share | בעלים/נמען בהתאם לפעולה | הרשאות ומצב עדכניים; סיום שיתוף + snapshot פנימי + סיום הקצאות אטומיים; SEC01 נשמר |
| rename/merge_taxonomy | בעלים | שינוי הסיווג וכל המשימות/הצעדים המושפעים בטרנזקציה אחת, עם גרסאות ו־preview |
| patch_settings | בעל החשבון | revision להגדרות; שינוי חלקי, בלי שמירת משימות |
| import/restore | מסלולים מפורשים, לא saveCloudTasks | כללי סעיף 9; אין עקיפה של גרסאות, מספרים או הרשאות |

כללי המוצר הקיימים נשמרים: סטטוס open עם צעד done מתורגם ל־in_progress; אין סגירה אוטומטית של משימה בגלל שכל צעדיה סגורים. כניסה ל־done קובעת completedAt, יציאה ממנו מנקה אותו; שינוי תוכן בלבד אינו משנה תאריך סיום. timestamps מגיעים מהשרת; משמעות תאריך ללא שעה נשמרת כערך תאריך, לא לפי שעון מכשיר שעלול להיות שגוי. אין שינוי סמוי בכללי dueDate הקיימים במסגרת החוזה.

rename אינו נשען על רשימה חלקית מהדפדפן. יצירה/שינוי סיווג מתואמים עם גרסת taxonomy, כדי שיצירה מקבילה לא תחזיר שם ישן אחרי מיזוג. פעולה רחבה חורגת ממגבלת בקשה אינטראקטיבית תידחה במפורש למסלול תחזוקה מאושר, ולא תפוצל לשמירות חלקיות נסתרות. מגבלות גודל/משך מספריות ייקבעו וייבדקו בחבילות 5–6, לא ייחשבו קיימות כיום.

## 6. לקוח, טיוטות וקריאות

| מצב לקוח | מה רואים ומה מותר |
|---|---|
| draft | טיוטה מקומית לפי משתמש, יעד וגרסת בסיס; לא מסומנת שמורה בענן |
| submitting | operationId ותוכן בלתי משתנה נשמרו לפני השליחה; אותו כפתור אינו יוצר פעולה חדשה |
| saved | התקבל receipt committed עם זהות וגרסה מוסמכות |
| unknown | נשלח אך לא התקבלה הכרעה; הטיוטה ומזהה הפעולה נשמרים לבדיקה/ניסיון חוזר בטוח |
| failed | דחייה סופית ידועה; תיקון כוונה ואישור חדש יוצרים operationId חדש |
| conflict | בסיס+שרת+טיוטה מוצגים; אין מחיקה של הטיוטה ואין הכפתור ״המשך״ בלי הסבר מה יישמר |
| read_only / upgrade_required | צפייה וטיוטה אפשריות לפי ההרשאה; שליחה חסומה עד תיקון המצב |

- יומן קטן לפעולות שכבר נשלחו נשמר לפי משתמש ומזהה פעולה. זה אינו תור המאפשר עריכת offline מלאה ואינו מתזמן אוטומטית אוסף שינויים. שמירת יומן נפרדת לכל פעולה מונעת מלשונית אחת לדרוס יומן של אחרת.
- אם שמירת הטיוטה/מזהה הפעולה בדפדפן נכשלת, מוצגת אזהרה לפני יציאה/רענון ולא ניתנת הבטחה לעמידות. ה־ledger בשרת עדיין מונע ביצוע כפול כאשר אותו מזהה זמין.
- ללא חיבור, טיוטה חדשה אינה נשלחת אוטומטית בהתחברות בלי בדיקת גרסה והצגת ההקשר הנדרש. פעולה שנשלחה והתוצאה שלה unknown מטופלת לפי אותו operationId, לא כאישור חדש.
- יציאה או מעבר חשבון מבודדים טיוטות ותגובות. ביטול fetch אינו מבטל COMMIT שכבר התרחש. אין replay של פעולה מחשבון קודם תחת חשבון חדש.
- GET, polling, focus ו־storage events אינם משנים נתונים ואינם מפעילים save. עדכון מטמון אינו כוונת משתמש חדשה.
- קריאות אוספות תוצאה מלאה או מסמנות במפורש חלקיות. אם נדרשת pagination, cursor קשור ל־change_seq; שינוי בזמן האיסוף מחייב רענון/התחלה מחדש ולא השוואת מחיקות על רשימה לא מלאה.
- משיכה מעדכנת בסיס שרת, לא מוחקת overlay של טיוטה/unknown. לכל יעד מופעל לכל היותר שינוי אחד ממתין מהלקוח; עריכות נוספות נשארות טיוטה עד שיודעים את גרסת הבסיס החדשה.
- ברירת המחדל של v1 היא **לא למזג אוטומטית גם שדות שונים** כשגרסת הבסיס השתנתה. מותר להציע מיזוג, אבל מוצג diff ונדרש אישור. זו בחירה שמרנית להיקף השימוש הקיים; אופטימיזציה עתידית נפרדת.
- אם השרת השתנה שוב בזמן הצגת ה־diff, ההכרעה נשלחת עם הגרסה שהוצגה; שינוי נוסף מחזיר conflict חדש, לא force overwrite.

## 7. AI ושיתוף: אותו חוזה, לא נתיב עוקף

- הצעת AI אינה כתיבה. פקודת הביצוע מפנה למזהה הצעה שמור, לייצוג מאומת שלה ולגרסאות שאושרו. השרת לא מבצע JSON חופשי או סומך על action_status שהלקוח כתב.
- לפני ביצוע נבדקים ההצעה, actor, בעלות/שיתוף, הרשאה נוכחית וגרסת המשימה. שינוי יעד או פרטי הצעה מחייב אישור מעודכן.
- ביצוע משימה ו־receipt/result של ההצעה מתחייבים באותה טרנזקציה. claim ייחודי להצעה מונע ביצוע כפול גם אם שני מכשירים שלחו operationId שונים.
- timeout משאיר מצב unknown; הצלחת המודל אינה done עסקי. הודעה ושיחת AI יכולות להישמר בנפרד, אך חיווי ביצוע משימה נובע מתוצאת הטרנזקציה בלבד.
- סינון/פתיחת תצוגה הם פעולות מקומיות ואינם מוצגים כשמירה בענן. מחיקת/ארכוב שיחות ממשיכים בחוזי ההרשאה שלהם, לא דרך כתיבת task כללית.
- תפקיד contributor אינו מקבל עריכת כותרת, הערות או כל מערך הצעדים. viewer אינו כותב. כללי עדכון צעד שהוקצה נשמרים; אין הרחבת סמכויות כחלק משינוי התשתית.
- שינוי הקצאה וביטול שיתוף חייבים להתחרות על אותו גבול כתיבה כמו עדכון צעד. הסדר שבו הטרנזקציות התחייבו קובע: אחרי ביטול שהתחייב אין עדכון חדש מהנמען.

## 8. סגירת מסלולי עקיפה

כל מסלול W01–W13 ו־S01–S11 במפת חבילה 1 מחויב למיפוי לפקודה או לקריאה ללא side effect. אין להשאיר מסלול ישן ״זמנית״ כשהשרת כבר מבטיח הגנה.

- גישת לקוח ישירה ל־INSERT/UPDATE/DELETE בטבלת tasks תישלל בעת המעבר; RLS לבעלות אינו תחליף לכך. אין לשלול SELECT מורשה בטעות.
- RPC עסקי חדש בודק auth והרשאה ואינו מקבל actor מהלקוח. אם תתווך שכבת Next, היא משתמשת בזהות המאומתת; service_role אינו מועבר לדפדפן.
- RPC קיימים לשיתוף/הקצאה/שחזור יועברו לאותו חוזה או ייחסמו בכתיבה עד להשלמת ההתאמה. אין helper פתוח בדומה ל־SEC01.
- פרוטוקול מינימלי/epoch נבדקים בשרת ובמסד. אי אפשר לעקוף אותם על ידי הוספת header מהלקוח הישן.
- גם operator SQL, ייבוא ושרת עם service_role אינם פטורים מנוהל התחזוקה והבדיקות. קריאת שירות עם מפתח חזק אינה הוכחה שהשינוי בטוח.
- rollback של frontend אינו מחזיר הרשאות DML ישנות, אינו מוריד epoch ואינו פותח שוב את SEC01. כשאין client תואם, המערכת נשארת בקריאה בלבד.

## 9. ייבוא, שחזור ומונים

ייבוא רגיל אינו שחזור. לפני כתיבה מוצגים מקור הקובץ, בעלות/מיפוי, רשומות חדשות, רשומות קיימות, שדות שונים ורשומות שנדחו. קובץ ישן עם P/W בלבד אינו מוכיח שהוא מתייחס לאותה משימה או לאותו חשבון.

- עדכון משימה קיימת דורש זיהוי מפורש ו־expectedRevision מהתצוגה שאושרה. אין החלפה אוטומטית לפי P19 בלבד.
- יצירה מקובץ חיצוני עוברת דרך allocator. אם נדרש מספר שונה ממספר המקור, מוצג מיפוי ונדרש אישור מפורש; אין שינוי במספר של רשומה קיימת. בלי הכרעה, השורה נשארת טיוטה/נדחית.
- שימור מספר היסטורי שאינו ברשימה הוא מסלול שחזור נבדק, לא יצירת לקוח במספר נבחר. אין שימוש מחדש במספר שנצרך רק משום שהרשומה אינה בקובץ הנוכחי.
- bulk הוא יחידה אטומית בגבולות הבקשה שהוגדרו. כשל הרשאה/גרסה/אילוץ עוצר את היחידה, ולא מציג ״הייבוא הושלם״ אחרי כתיבה חלקית.

שחזור חי מחייב חלון read_only, צילום חדש ותרגול. לאחר אישור: שחזור תוכן שומר UUID/P/W/מזהי צעדים, אינו מחזיר הרשאות שיתוף שבוטלו אוטומטית ואינו מחזיר מונים או receipts לאחור. epoch חדש מפריד את המצב המשוחזר מכל הלקוחות הישנים. revisions לא חוזרים לערכים מהקובץ; נשמרת מונוטוניות או נקבעים ערכים חדשים יחד עם epoch חדש, בהתאם לסכמת המימוש.

בקשה ישנה שכבר התחייבה לפני שחזור יכולה לקבל receipt היסטורי מצומצם, אך אסור להחיל את תוצאתה הישנה על המטמון החדש. בקשה ישנה שלא התחייבה נדחית ב־epoch ולא מבוצעת אחרי השחזור ללא בחינה מחדש. high-water הוא לפחות המקסימום של המצב הקיים, ה־ledger הרלוונטי, snapshots שנבדקו והקובץ המשוחזר; חסם לא ידוע עוצר הקצאה בטוחה עד בירור, לא מוביל לניחוש.

כל שינוי סכמה למימוש החוזה מחייב עדכון export/תרגול הגיבוי לפני שמסתמכים עליו. כלי חבילה 2 נכשל במכוון על column drift; הגיבוי הנוכחי אינו מכיל עדיין counters/epochs/ledger חדשים. בהשבת מצב אחרי מיגרציה יש לתכנן שימור של נתוני הבקרה החדשים, ולא להעתיק אותם מקובץ ישן.

אין החלטות מוצר חוסמות חדשות לחבילה זו: נשמרו הסכמות אסף על מספרים קבועים, diff לפני הכרעה, טיוטות בלבד ללא חיבור, עצירה מתואמת ועותק גיבוי מקומי בלבד. תזמון גיבוי, עותק מחוץ למחשב ומדיניות משפטית אינם נפתרים על ידי חוזה השמירה ונשארים מתועדים בנפרד. מגבלות בקשה מספריות ותצוגות מדויקות ייקבעו בחבילות הייעודיות לפני מימוש, לא ייחשבו הנחות שנבדקו.

בדיקת חבילה 3: התאמה למפת הכותבים, כללי המוצר, SEC01 וגבולות הגיבוי; `git diff --check`. אין שינוי ריצה, migration, קריאת נתוני אמת או פריסה; lint/build יידרשו כשישתנה קוד בחבילות המימוש.
