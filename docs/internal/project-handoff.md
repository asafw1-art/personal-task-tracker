## אופן העבודה עם אסף

### משמעות בקשת ביצוע

- כאשר אסף אומר "בצע", "קדימה" או מאשר חבילה, הציפייה היא לביצוע מלא: מימוש, בדיקות, תיקונים, תיעוד, commit, push, פריסה ו-QA ב-Production.
- אין לעצור לאחר כתיבת הקוד רק כדי להציע את יתר השלבים.
- עוצרים רק כאשר קיימת חסימה אמיתית, התנגשות עם עיקרון קיים, החלטת מוצר מהותית שחסרה, פעולה חיצונית שדורשת את אסף או סיכון לחריגה מהקצאת הטוקנים.

### מתי לשאול

- לשאול לפני ביצוע אם המשימה עמומה, לא סבירה, סותרת החלטה קודמת או יכולה לגרום לאובדן נתונים.
- לרכז שאלות יחד. אין לעצור שוב ושוב על בחירות טכניות שאפשר להכריע באופן שמרני לפי הקוד הקיים.
- כאשר קיימות חלופות UX אמיתיות, להציג המלצה ודעה מקצועית ולא רק רשימת אפשרויות.

### תקשורת

- לכתוב בעברית ברורה, ישירה וממוקדת.
- לעדכן בתחילת עבודה, בממצא מהותי ובסיום; לא לדווח על כל קריאת קובץ.
- להסביר מונחים טכניים כשיש סיכוי שאינם ברורים.
- לא להכריז שהמשימה הושלמה לפני שהגרסה הנכונה נפרסה ונבדקה.
- אסף מעדיף לראות כיווני UX ניסיוניים בפועל ואז להחליט אם להשאירם.
- לפני תחילת כל חלק מימוש, ההודעה הראשונה היא המלצה על מודל Codex ורמת חשיבה שמתאימים למורכבות החלק ולמכסה הזמינה, יחד עם תקציר קצר של החבילה. עוצרים שם ללא הפעלת כלים או התחלת קוד, כדי שאסף יוכל להחליף מודל; מתחילים רק לאחר אישורו להמשיך.

### חיסכון בטוקנים

- ברירת המחדל היא להמשיך בשיחה אחת. להציע שיחה נוספת רק כשיש יתרון חריג וברור.
- מתחת ל-10% מההקצאה אין לבצע פעולה אקטיבית ללא אישור מפורש.
- להשתמש בחיפושים ממוקדים, להגביל פלטי כלים ולהימנע מקריאה חוזרת של מסמכים שלמים.
- לעבוד על חבילה אחת בכל פעם ולתעד בסיום שורה קצרה במקום לשחזר את כל ההיסטוריה.

- אסף הוא בעל המוצר והמשתמש המרכזי, ובודק את האפליקציה גם במחשב וגם בנייד.

- שימושיות בפועל חשובה יותר מפתרון שנראה תקין רק בקוד.
- הוא רוצה לדעת בכל שלב מה הושלם, מה נשאר ומה מומלץ לבצע לאחר מכן.
- הוא מצפה לעצמאות מקצועית לאחר אישור הכיוון, אך לא להרחבת תכולה ללא תיאום.

## הגדרת "בוצע"

משימה נחשבת סגורה רק כאשר כל הסעיפים הרלוונטיים התקיימו:

1. המימוש הושלם ללא שינויי צד לא נחוצים.
2. `npm run lint` ו-`npm run build` עברו.
3. בוצע QA ממוקד במובייל ובדסקטופ ובמצבים הרלוונטיים.
4. נוצר commit ממוקד ונשלח ל-`main`.
5. Vercel סיימה את הפריסה וה-DOM בפרודקשן מוכיח שהגרסה החדשה פעילה.
6. אם נמצא כשל ב-QA, הוא תוקן ונבדק מחדש.
7. ה-Backlog, ההחלטות ויומן הביצוע עודכנו לפי הצורך.
8. לא צורפו ל-commit קבצים או שינויים שאינם קשורים למשימה.

## מטריצת אישורים

- קריאת קוד, עריכה ממוקדת ובדיקות מקומיות לא הרסניות: חלק רגיל מהביצוע.
- commit, push ופריסה: כלולים כאשר אסף אישר ביצוע מלא.
- SQL ב-Production, יצירת OAuth והזנת secrets: דורשים אישור או פעולה מודרכת של אסף.
- מחיקת נתונים, שחזור גיבוי, איפוס או שינוי בלתי הפיך: דורשים אישור בזמן הפעולה.
- שינוי תכולה מהותי, ספק חיצוני חדש או עלות חדשה: תיאום מראש.
- אין לגעת בשינויים קיימים ולא קשורים ב-worktree. בפרט, תיקיית `exports/` נשארת מחוץ ל-commits אלא אם המשימה עוסקת בה.

## עקרונות UI ו-UX

- תוכן המשימה הוא המידע הבולט ביותר בכרטיס; פעולות ומטא אינן דוחקות אותו.

- פעולות משניות מוצגות באייקון מוכר, עם `aria-label` ו-tooltip; אייקונים חדשים נלקחים מ-`lucide-react` כשאפשר.
- כפתור ברוחב מלא שמור לפעולה ראשית או לאישור משמעותי.
- אין להוסיף כרטיסים בתוך כרטיסים או רצועות בקרה גבוהות ללא צורך.
- יש לבדוק מצב בהיר וכהה, RTL, טקסט ארוך, overflow, safe-area ומקלדת מובייל.
- חלונית חוסמת נועלת את גלילת הרקע ומסתירה כפתורים צפים שעלולים לכסות תוכן.

## אבטחה ונתונים

- Supabase הוא מקור האמת לנתוני הענן.
- RLS ו-RPC מאובטח אוכפים הרשאות; הסתרה ב-React אינה שכבת הגנה.
- אין להשתמש ב-service role או ב-secrets ב-frontend.
- `/api/assistant` מאמת Bearer token מול Supabase לפני שימוש בספק AI.
- כל פעולת AI שמשנה נתונים דורשת Preview ואישור מפורש. אין מחיקה או ביטול גורפים.
- משימה משותפת נשארת בבעלות היוצר. משתתף רואה את המשימה כולה אך יכול לבצע רק פעולות שהוגדרו לו ב-RPC.
- כוכב/מיקוד של משתתף הוא אישי ואינו משנה את סימון הבעלים.
- היסטוריית שיתוף והקצאות נשמרת; לאחר סיום שיתוף המשתתף רואה תצלום היסטורי ולא נתונים עתידיים.
- גיבוי Drive הוא אופציונלי. שחזור דורש Preview, אישור וגיבוי `pre_restore`.

## סביבת הרצה, הגדרות ופריסה

- פקודות העבודה הן `npm run dev`, `npm run lint`, `npm run build` ו-`npm start`. אין בדיקות אוטומטיות נוספות המוגדרות כרגע ב-`package.json`.
- משתני client מותרים: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` ו-`NEXT_PUBLIC_APP_URL`. משתני שרת כוללים את מפתחות Supabase, Google Drive, הצפנת token, Cron וספק AI. שמות מלאים מפורטים בגרסה העמוקה ובמסמך הגדרת Drive; לעולם אין להעתיק את הערכים עצמם לתיעוד או לפלט.
- push ל-`main` מפעיל פריסת Vercel. הצלחת push אינה מספיקה: יש להמתין פעם אחת לפריסה ולוודא ב-Production שה-DOM או ההתנהגות החדשה אכן פעילים.

## מחזור חיי נתונים וסנכרון

- משימות נשמרות מקומית לצורך זמינות ומסתנכרנות ל-Supabase לאחר התחברות. קוד חדש חייב לעבוד עם נתונים קיימים ולא להניח שהענן, local storage וה-taxonomy נטענים באותו רגע.
- יש להבדיל בין `id` המקומי הקנוני, `cloudId`, בעלות, `shareId` ותצלום היסטורי. משימה משותפת אינה הופכת למשימה בבעלות המשתתף.
- תאריך יעד הוא date-only ונשמר לענן בשעה ניטרלית שנבחרה כדי למנוע drift בין אזורי זמן. אין לשנות את האסטרטגיה ללא migration ובדיקת נתונים קיימים.
- שינויים בשיתוף, הקצאות, כוכב אישי וסטטוס צעד עוברים דרך הפונקציות וה-RPC הייעודיים ולא דרך כתיבה כללית לטבלת משימות.

## נוהל שחרור ו-QA

- לפני commit: לבדוק diff ממוקד, `git diff --check`, lint ו-build. לאחר שינוי קוד שנעשה בעקבות כשל יש להריץ שוב את הבדיקות שנפגעו.
- QA מחובר מתבצע סמוך לסוף ורק לזרימות שהשתנו. שינוי מובייל נבדק לפחות ברוחב צר ובדסקטופ; שינוי חזותי רוחבי נבדק גם בהיר וכהה; שינוי הרשאות נבדק עם שני משתמשים אמיתיים.
- אין לשנות נתוני Production רק כדי לבדוק UI. כאשר בדיקה דורשת פעולה אמיתית, להשתמש בפעולה הפיכה או לבקש אישור. בסיום יש לסגור חלוניות, להחזיר viewport ולוודא שלא נשאר מצב בדיקה פעיל.

## התאוששות, Rollback וטיפול בתקלה

- אם פריסה חדשה שוברת את האפליקציה, קודם לאסוף סימן כשל ממוקד ולבודד את ה-commit. אין להשתמש ב-`git reset --hard` או למחוק שינויים של המשתמש; תיקון מועדף הוא commit מתקן או revert מפורש ומאושר.
- אם התקלה נוגעת לנתונים, לעצור כתיבות, לבצע Preview של גיבוי רלוונטי ולשחזר רק לאחר אישור. מנגנון Drive יוצר `pre_restore`, אך אינו מחליף בדיקת RLS או הבנת היקף הפגיעה.
- אם OAuth, Cron או ספק AI אינם זמינים, האפליקציה צריכה להמשיך לאפשר ניהול משימות. יש לדווח על השירות שנפגע ולא לבצע איפוס חשבון, חיבור מחדש או החלפת secrets ללא אבחון ואישור.

## סדר העבודה המומלץ

1. QA שימוש אמיתי קצר לכל חבילה חדשה וליטוש רק לפי ממצא.
2. תצוגת לוח שנה פנימית: חודש ושבוע, יעדים, עומס, סינון ופתיחת משימה.
3. תזכורות חכמות לפי זמן, כולל שעות שקטות ומניעת הצפה.
4. סנכרון Google Calendar חד-כיווני ומבוקר לפני Outlook או סנכרון דו-כיווני.

זהו סדר מומלץ, לא אישור ביצוע. המקור לסטטוס ולהערכות הוא `project-backlog.md`.

## אל תחזור על הטעויות האלה

- push מוצלח אינו הוכחה שהפריסה כבר פעילה. יש להמתין ל-Vercel ולבדוק את הגרסה בפרודקשן.
- בדיקה לא מחוברת אינה מספיקה למסכים התלויים במשתמש, שיתוף, Admin או נתוני ענן.
- אין להסתמך על UI לאכיפת הרשאות; יש לבדוק RLS/RPC.
- אין לבצע החלפת נתונים שקטה כדי לתקן פורמט או תאריך.
- `overflow` של הורה עלול לשבור `position: sticky`; במקרה הקיים נעשה שימוש ב-`overflow-x: clip`.
- מקלדת מובייל מחייבת התחשבות ב-`VisualViewport`, safe-area וגלילת תוכן עצמאית.
- אין להציג כמה התראות כניסה רצופות; ההתראות מאוחדות לחלונית אחת עם פירוט לפי סוג.
- אין להחזיר שורת הוספה מהירה למסך הראשי; כפתור `+` הוא נתיב ההוספה המרכזי.
- אין להפוך פעולות חוזרות ומשניות לכפתורים רחבים שמגדילים את הכרטיסים.
- אין למחוק החלטות או היסטוריה רק כדי לקצר תיעוד; קוראים אותן באופן ממוקד.

## מפת קוד קצרה

- `src/app/page.tsx` - הממשק הראשי ורוב זרימות המוצר.
- `src/app/globals.css` - מערכת העיצוב וההתאמות הרספונסיביות.
- `src/lib/tasks.ts` - מודל משימות, מזהים ונרמול.
- `src/lib/supabase*.ts` - שכבות הנתונים לפי תחום.
- `src/app/api/assistant` - API לעוזר המשימות.
- `src/app/api/drive` ו-`src/app/api/cron/drive-backups` - חיבור וגיבוי Drive.
- `supabase/` - migrations ו-RPC. אין להריץ סקריפט מחדש בלי להבין אם הוא idempotent.
- `docs/internal/` - Backlog, החלטות, יומן ותוכניות נקודתיות.

`page.tsx` ו-`globals.css` גדולים. אין לקרוא אותם במלואם כברירת מחדל; יש לאתר רכיבים ומחלקות באמצעות `rg`.

## תחזוקת המסמך

- לעדכן תאריך, commit אחרון, חבילות שהושלמו והמשימה המומלצת אחרי שינוי מהותי.
- לשמור את המסמך קצר ומבצעי. פרטים כרונולוגיים נשארים ביומן הביצוע.
- הוראות מערכת ומפתח גוברות; הוראת אסף מפורשת ועדכנית גוברת על הנחיות קובצי הפרויקט. בהיעדרה פועלים לפי `AGENTS.md` וההחלטות המתועדות.
- אם הוא סותר החלטה חדשה ומתועדת, יש לתקן אותו באותו commit ולא להשאיר שתי גרסאות אמת.
